Security Model

Defence in Depth — 5 Layers

L1
Filesystem Sandboxing
Only /workspace is bind-mounted. Claude cannot touch host system files, other projects, or home configs
L2
Non-Root Execution
remoteUser: "developer" — Claude Code rejects --dangerously-skip-permissions when run as root
L3
Network Egress Firewall
Default-deny iptables. Only api.anthropic.com, GitHub, npm — prevents data exfiltration
L4
Managed Settings (Highest Precedence)
/etc/claude-code/managed-settings.json overrides ALL user settings. Deny .env*, *.pem, credentials
L5
Secret Hygiene
Never mount ~/.ssh, ~/.aws. Use SSH agent forwarding or repo-scoped tokens instead
Even with --dangerously-skip-permissions, the blast radius is limited to the container + workspace bind mount
Advanced

WASM Sandboxing — Beyond Containers

WebAssembly provides a capability-based security model that complements container isolation. Consider WASM for build tools and untrusted code execution inside your dev container.

Capability-Based Security
WASM modules have zero ambient authority. No filesystem, network, or env var access unless explicitly granted via WASI. A WASM-compiled linter can read your source but physically cannot phone home
Deterministic Builds
WASM binaries are platform-independent. Same binary runs on macOS ARM, Linux x86, Windows — no cross-compile matrix needed in your devcontainer
Instant Startup
WASM modules cold-start in milliseconds vs seconds for containers. Ideal for ephemeral tool execution triggered by Claude Code
Use cases inside dev containers
🔍
Sandboxed linters & formatters
Run untrusted linter plugins in WASM — they can read source but can't access network or filesystem beyond what you grant
🧪
Untrusted code execution
Claude generates code → compile to WASM → test in sandbox — no container escape risk even if code is malicious
📦
Supply chain defence
Run npm/cargo build scripts in WASM to prevent compromised packages from executing arbitrary host commands
🌐
Cross-platform MCP servers
WASM-compiled MCP servers run identically on every platform — no per-OS binary builds
The Template

What You Get

Copy .devcontainer/ into your repo. Four files, fully commented.

.devcontainer/
devcontainer.json Mounts, env vars, firewall, non-root user
Dockerfile Hardened image + Claude Code install
managed-settings.json Org policy (overrides user settings)
init-firewall.sh Default-deny egress + domain allowlist
Key security highlights
// devcontainer.json
"remoteUser": "developer",
"workspaceMount": "source=...,target=/workspace,type=bind",

// Dockerfile
COPY managed-settings.json /etc/claude-code/

// managed-settings.json
"deny": ["Read(.env*)", "Read(*.pem)"],

// init-firewall.sh
iptables -P OUTPUT DROP
iptables -A OUTPUT -m set
  --match-set allowed-domains dst -j ACCEPT

Security Comparison

Bare Metal vs Dev Container vs WASM

Threat Bare Metal Dev Container + WASM
Host file modification ❌ Full access ✅ Bind mount only ✅ Bind mount only
Secret exfiltration ❌ All host secrets ✅ Firewall blocks ✅ No network access
Supply chain attack ❌ Full host access ⚠️ Container scope ✅ No ambient auth
Malicious build script ❌ Runs as user ⚠️ Container user ✅ WASI sandbox
Cross-project contamination ❌ Shared filesystem ✅ Isolated workspace ✅ Isolated workspace
Env consistency ❌ Drift ✅ Deterministic ✅ Deterministic
